# Работа над CVTL

- Использовать встроенные средства Codex для делегирования. Разделять авторство и проверку. Вести работу по `docs/PLAN.md`, фиксировать доказательства и пробелы в `docs/STATUS.md`.
- Пока закладывается фундамент проекта, каждый коммит проходит независимое ревью GPT-6 Astra. Перед коммитом передать на проверку точный staged diff или дерево. Проверить границы модулей, корректность, безопасность, простоту решения и свидетельства тестов. Исправить замечания и повторить ревью, если содержимое дерева изменилось. Снять это правило можно по указанию пользователя.
- Обязательный гейт каждого ревью Astra — `Simplicity: PASS` или `Simplicity: BLOCK` с кратким обоснованием. Проверить, какие существующие пути можно переиспользовать и какие новые слои, состояния, зависимости или тестовые механизмы можно убрать без потери требований. Блокировать по конкретному упрощению или лишней сложности с указанием места и последствий. Коммит допускается после общего PASS и PASS по простоте на одном точном дереве.
- Фаза A проходит без физического доступа к приборам, включая поиск VISA-ресурсов, опрос и проверку соединения. Конфигурации по умолчанию имеют `hardware_enabled: false` и `null` в полях аппаратных ограничений. Числа для сценариев допустимы в профилях `test_only`.
- Целевая ОС — Ubuntu Linux 22.04 LTS. Для стенда учитывать существующие PyVISA и GPIB–USB. Аппаратные сведения и допуски уточнять по первоисточникам и отдельной проверкой на стенде.
- `stage1` — тёплая ступень, `stage2` — холодная. Интерфейс на русском, идентификаторы в коде на английском.

## GRACE с M6 по M9

- Использовать GRACE CLI 4.2.1 из `osovv/grace-marketplace` на коммите `70f5ec4305bb2cc6ed82dea9470a3b810603874b`. Инструмент ставится отдельно от runtime проекта. [ADR 0009](docs/adr/0009-grace-adoption.md)
- Требования задают `TZ.md`, `GOAL.md`, `docs/PLAN.md` и принятые ADR. `.grace` описывает фактические границы модулей и проверяемые изменения. При расхождении остановить затронутый пакет и согласовать исправление.
- Технические решения по коду делегированы независимой GPT-6 Astra. Она отдельно утверждает точную спецификацию (`SPEC: APPROVED`), затем отдельно план на фактической базе (`PLAN: APPROVED`), в обоих случаях с общим PASS и `Simplicity: PASS`. Применение программного пакета требует отдельного решения Astra на свежем `final`. Физические модели, параметры и допуски утверждает владелец физики.
- До соответствующего утверждения статус `draft`. Ожидание утверждения не даёт допуска к исполнению. Утверждённые scope, assertions и задачи не переписывать. При drift остановить пакет и пересогласовать.
- Приёмка и авторизация применения каждого пакета RECORDING делегированы новой независимой GPT-6 Astra. После свежего `final` она проверяет точное дерево, читаемость, переиспользование и отсутствие лишних слоёв. Для применения нужны общий PASS, `Simplicity: PASS` и явное `APPLY: AUTHORIZED`. Решения по физическим моделям, параметрам и допускам остаются за владельцем физики.
- В M6 порядок RECORDING → REPLAY → IMPORT. Первый цикл последовательный, с одним пишущим исполнителем. История M0–M5 сохраняется без applied-пакетов задним числом.
- Перед исполнением проверять baseline утверждённого плана, после исполнения — target и final. `--run-commands` допустим только после отдельного допуска к исполнению и просмотра leaf-команд в среде без доступа к приборам. В `MustPassCommand` указывать измеренный `budgetSeconds`, не вкладывать `grace lint` или `grace status`.
- Структурный lint дополняет прежние тесты и ревью точного дерева GPT-6 Astra. Разметку старых исходников добавлять только в явно согласованной области.
