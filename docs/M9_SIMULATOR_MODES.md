# M9. Операторские режимы симулятора

Локальный интерфейс открывает сценарии наблюдения, постоянной мощности, таблицы мощности, удержания `stage2` и виртуального тела. Выбор виртуального тела допускает добавочную нагрузку или экспериментальную компенсацию насадки. Запросы с явным режимом записываются в профиль `test_only_operator_modes_v1`. API без поля `mode` использует прежний профиль A1 v2.

## Контур и запись

- В наблюдении обе ветви подтверждают OFF, показания продолжают записываться. Запуск нагрева недоступен.
- Постоянная мощность и таблица проходят общий M4/M5. Таблица линейно интерполирует между узлами и удерживает последнее значение. Время отсчитывается от принятого кадра Start с подтверждённым ON.
- Hold использует одну измеренную пару `stage1/stage2` с возрастом по старейшей отметке. При просрочке или инверсии M5 фиксирует свою причину и отключает обе ветви.
- Виртуальное тело использует `stage2` или `tf` как температурную границу моста. Модель нагревателя вводит измеренную энергию обеих ветвей в узел `tf`. Смена порта меняет расчёт потока моста. Место ввода энергии в синтетической головке задаётся моделью.

Сначала интегрируется интервал со старыми параметрами и ранее принятым показанием выбранного порта. Затем проверяется и целиком применяется кандидат на замену массы, масштаба, материала и моста. При изменении тела температура сохраняется, в raw отдельно записывается `dH_event = H_new − H_old`. Изменение только моста сохраняет энтальпию. Пригодность кандидата повторно проверяется по состоянию на конце интервала. Принятый журналом результат обновляет операторскую проекцию по номеру записи.

Контур записывает входы до допуска команды и использует прежний путь подтверждения обеих ветвей. Если удержанное измерение слишком старое для теплового расчёта, журнал фиксирует отказ модели без искусственного интервала. При насыщении ограничение мощности видно отдельно, тепловое время продолжается по фактически поданной энергии.

## Синтетические условия

Обычная головка начинает с `stage1=45 К`, `stage2=15 К`, `tf=16 К`. Ёмкости трёх узлов составляют 10, 20 и 5 Дж/К. Проводимости связей `stage1–stage2` и `tf–stage2` составляют 0,05 и 0,5 Вт/К. Hold использует отдельный эталон с начальными 20, 15 и 15,75 К, ёмкостями 10, 2 и 2 Дж/К, связью `tf–stage2` 1 Вт/К и холодным отводом 0,75 Вт. Уставка 15,2 К, коэффициенты 2 Вт/К и 0,5 Вт/(К·с). Предельный возраст для Hold составляет 150 мс. Эти числа относятся к `test_only`.

Экспериментальная компенсация использует опись насадки и явно заданный `Q_par_f`. Для расчёта головки теплоёмкость берётся при модельном `tf` на начале интервала. Для запроса используется измеренная `tf` и причинная производная по двум принятым чтениям канала 3.

```text
P_req = q_v + Cf(tf) × (tf_now − tf_prev) / (t_now − t_prev) − Q_par_f
```

На эталоне 0,2 кг OFHC при 16 К дают `Cf ≈ 0,7290878 Дж/К`. Для пары 16,01 → 16,00 К за 0,1 с, потока 0,28 Вт и притока 0,05 Вт запрос составляет около 0,1570912 Вт. `q_v`, знаковый `P_req`, ограниченная мощность и измеренное `U × I` доступны раздельно. До пригодной пары нагрев заблокирован. Отрицательный запрос подтверждает OFF обеих ветвей, а повторный запуск требует свежей пары и действий оператора. Переменная `Cf` отмечается отдельной причиной недоступности оценки M8.

## Воспроизведение

```sh
cargo test --locked -p cvtl-sim --test operator_modes
cargo test --locked -p cvtl-store --test records
cargo test --locked -p cvtl-cli --test operator_modes
cargo test --locked -p cvtl-cli --test operator_modes hold_tracks_stage2_on_loopback -- --ignored --exact --nocapture
cargo test --locked -p cvtl-daemon --test operator_http
npm --prefix ui run build:operator
npm --prefix ui run test:operator
```

Реплей пересчитывает интервалы, поток, правки и компенсацию из raw и архивного каталога. Температуры и отметки удержанного наблюдения сверяются точно, пересчитанные тепловые величины имеют численный допуск. Новый профиль расширяет CSV и Parquet условиями режима. Прежние отчёты и производные файлы сверяются побайтно.

## Результаты офлайн-проверки

На macOS ARM64 и Ubuntu 22.04.5 ARM64 с Rust 1.94.1 прошли форматирование, сборка, Clippy с `-D warnings`, по 337 Rust-тестов и запуск демона с конфигом поставки. Длительный тест Hold запускался отдельно на каждой ОС. Таблица содержит диапазоны последних 20 отсчётов из 200.

| Среда | Температура `stage2`, К | Фактическая мощность, Вт |
|---|---:|---:|
| macOS ARM64 | 15,195–15,196 | 0,751861–0,756930 |
| Ubuntu 22.04.5 ARM64 | 15,195–15,196 | 0,751940–0,756972 |

Офлайн-сборка и полный браузерный сценарий прошли на обеих ОС с Node 22.23.4. Проверены прежний A1 с 250 тактами, историческая таблица при ширине 360 CSS px, все явные режимы, запись изменений и отказов, разбор и экспорт. Реплей связывает метку компенсации с проверенным снимком. Браузерный тест ждёт принятый такт конкретного прогона. Это устранило гонку первого браузерного прогона на Ubuntu, который мог читать ещё не обновлённый ответ API.

На каждой ОС пять контрольных JSON для RECORDING, A1 и M8 и четыре файла контрольного экспорта M8 совпали с эталонными байтами. В расширенной схеме тест readback проверил знаковый запрос, отдельный поток, нулевую цель, пропуски, принятые параметры и SHA-256 источников. Пустой префикс получил схему из проверенного профиля. Ubuntu проверялась в локальной VM, в сетевом пространстве только с `lo`. Журналы, SHA-256 снимка исходников и снимки браузера сохранены в `.local/GRACE-M9-SIMULATOR-MODES/`.
